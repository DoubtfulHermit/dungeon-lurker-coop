# Task: Co-op patch-point analysis of Dungeon Lurker (decompiled Unity game)

You are analyzing the decompiled C# source of "Dungeon Lurker Demo", a single-player Unity 6 (Mono) roguelike dungeon crawler, to prepare a **local couch co-op mod** built with BepInEx 5 + Harmony. The decompiled source is in `reference/decompiled/` (376 files, full symbol names from shipped PDBs).

Goal of the mod (context, not your task): clone the in-scene `Player` at level load as P2, pair P2 to a second gamepad via Unity InputSystem, camera follows midpoint of living players, game-over only when ALL players are down.

## Your task
Read the relevant decompiled sources carefully and write a precise engineering report to `notes/seams-report.md`. For every claim, cite file + method. No speculation without marking it as such. Cover:

1. **Player lifecycle**: Is `Player` baked into each level scene or instantiated? Trace `Player.Initialize`, `Actor.Initialize`, `LevelManager.RegisterActor`, and what happens to the player object across `LevelTransition`/`SceneManager.LoadScene` (destroyed and re-created per scene? DontDestroyOnLoad?). Where do stats/HP/inventory live between floors (`DungeonMaster`? `SaveManager`?) — i.e., what state is shared vs per-Player-object. What would cloning the Player GameObject at scene load duplicate that MUST NOT be duplicated (registered singletons, HUD bindings, camera refs, listeners)?
2. **Input path**: Exact flow from hardware to `Player.Move`. `InputRelay` has a static `activeInput` (`UnityEngine.InputSystem.PlayerInput` component) — does the game's custom `PlayerInput` (component on the Player) read from that static, subscribe to events, or poll actions? What is the cleanest way to give a cloned Player its own isolated input source bound only to a specific `Gamepad` device (e.g. instantiate a second UnityEngine.InputSystem.PlayerInput with its own actions asset instance + `InputUser.PerformPairingWithDevice`)? Note any places where `InputRelay.instance`/statics would make P2 input leak to P1 or vice versa (UI navigation, action-map switching between "UI" and gameplay maps).
3. **Camera**: What does Cinemachine follow (which class sets Follow/LookAt, where)? `CameraManager` uses `Player.GetInstance()` in several places — list each use and whether it needs midpoint logic, a null-guard, or nothing. Identify the single best patch point for a midpoint-follow virtual target. Note `PixelController` player references too.
4. **Death & game-over**: Full path `Actor.Die` → `Player.UpdateDeath` → respawns (`DungeonMaster.CheckRespawns/UseRespawn`) → `MenuObjectGameOver`. Also `Resurrect` action and `CheckResurrect` (used by enemies?) — could they be reused for ally revive? Propose the concrete both-players-down patch.
5. **Single-player assumptions inventory**: Go through ALL references to `Player.GetInstance()`/`Player.instance` (24 files) and classify each: [SAFE for P1-as-instance] / [NEEDS patch — gameplay-breaking for P2] / [NEEDS patch — nice-to-have]. Especially `Trigger` (interaction), `Pitbox` (pit falls), `Encounter` (door locking/spawn logic), `LootContainer`, `ProjectileSpawner`, `Breakable`, `CustomEffect`, `PlayDead`.
6. **HUD**: How `HUDController`/`PlayerHUD`/`HealthBar`/`Magicbar` bind to the player. Minimal viable P2 health display (even just a duplicated health bar anchored elsewhere).
7. **Hazards for a clone-based approach**: anything on the Player prefab/object that is singleton-registered, name-lookup based, or animation-event based that would double-fire with two Players (sounds, SaveManager writes, StatTracker, TimerManager usage, `MenuController` interactions). List each with severity.

Be exhaustive on items 5 and 7 — they decide whether the mod ships. Write the report NOW to notes/seams-report.md; that file is the only deliverable.
